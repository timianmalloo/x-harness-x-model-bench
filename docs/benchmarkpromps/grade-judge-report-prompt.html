The prompt

You are grading, comparing and analysing lean benchmark runs that were run by the "lean benchmark run" prompt
(Prompt 1). You work in the main checkout, C:\Projects\x-harness-x-model-bench, alone: no sub-agents, no
coordination layer, no new worktree. Use `python`, never `python3` (Windows). Tokens are the only cost unit; never
write USD. Never print a token or credential.

RUNS (the operator pastes the HANDOFF lines, one per line):
  HANDOFF: <RUN_ID>@<WORKTREE>
  HANDOFF: <RUN_ID>@<WORKTREE>

GOAL: every listed run graded with the judges, and three HTML pages written and open in Chrome: (1) the grading
completion report, (2) the benchmark comparison with root causes, (3) the pack-on vs pack-off analysis with tuning
candidates. DONE WHEN: each run has a completed grading pass, `bench verify` passes on each copied run, the three
pages exist under docs/benchmark-reports/<REPORT_ID>/ and are open, and they are committed locally. NOT IN SCOPE:
running or re-running cells, editing bench code or the pack, changing a grade by hand, pushing.

    Record `git rev-parse HEAD` as BASE.
  - BENCH_OPERATOR_EMAIL is set (check it is non-empty; never print it). If it is empty, stop and ask.
  - HB_CLAUDE_OAUTH_TOKEN = the contents of C:\Users\malla\.harness-bench\claude-oauth-token.txt.txt, whitespace

  - REPORT_ID = report-<UTC yyyymmddThhmm>. OUT = docs/benchmark-reports/<REPORT_ID>.
  - `uv run bench tools install` (the judges use the pinned claude-code and copilot builds).

STEP 1 - read and check each run (for every HANDOFF line)
  - Read <WORKTREE>\runs\<RUN_ID>\handoff.json. Check run_id matches, "verify" is "ok", and note combo, harness,
    model, effort, context, pack, cells, cells_root.
  - `uv run bench --runs <WORKTREE>\runs status <RUN_ID>`: the run has ended (no cell running). A live run is a stop.
  - `uv run bench --runs <WORKTREE>\runs verify <RUN_ID>` must exit 0.

STEP 2 - bring the runs into the main checkout (one runs folder, so the reports can read them together)
  - `robocopy <WORKTREE>\runs\<RUN_ID> runs\<RUN_ID> /E /COPY:DAT /R:1 /W:1 /NP /NFL /NDL`. Robocopy exit codes 0-7
    are success; 8 or more is a failure (stop). Use robocopy, not a Git Bash `cp` (it has altered copied run files
    before, class MSYS-COPY-A).
  - `uv run bench verify <RUN_ID>` in the main checkout must exit 0. If runs\<RUN_ID> already exists and differs,
    stop and report; never overwrite a run.

STEP 3 - grade (one run at a time)
  - `uv run bench --cells-root C:\Projects\bench-cells\<REPORT_ID> grade <RUN_ID> --allow-model-calls`
  - It prints "graded N cell(s) in pass <grading_id>". Record the grading_id and N. N must equal the run's cell
    count. A refusal is reported verbatim (HB-GRD-005 means a run is live: wait and retry once; HB-USR-002 means the
    email is missing).
  - `uv run bench report <RUN_ID>` (writes runs\<RUN_ID>\report.html with the new pass).
  - `uv run bench verify <RUN_ID>` again: exit 0.

STEP 4 - page 1, the grading completion report
  - Write <OUT>/grading-completion.md, from `uv run bench status <RUN_ID> --json` and each report.html, with:
    one row per run (run id, combo, harness, model, worktree, cells, cells graded, grading_id, verify result,
    validity counts by code); per run, the cells that are invalid or ungraded and why (code and text); the judge
    calls made and missed per run; anything that did not grade, and what it would take to finish it.
  - Every number comes from the bench output. Label any number you computed as computed.
  - `python docs/ai-forward-pack/scripts/render-markdown.py <OUT>/grading-completion.md --open`

STEP 5 - page 2, the benchmark comparison (for the harness teams)
  - Generate it first with no analysis:
    `uv run bench report --cost-compare <RUN_ID> <RUN_ID> ... --out <OUT>/benchmark-comparison.html`
  - Read the generated page's tables. Then read the evidence behind each difference: per-cell tokens by part
    (fresh input, cache read, cache write, output, reasoning), requests per cell, prompt composition
    (runs/<RUN_ID>/prompt_parts), the served settings read back (runs/<RUN_ID>/served), tool and harness events
    (runs/<RUN_ID>/harness_events), wall time, and grade outcomes per task.
  - Write <OUT>/benchmark-comparison-analysis.md: for each harness, what drives its cost and its quality relative to
    the others, and the root cause where the evidence shows one (cache behaviour, request count, context re-sent per
    request, reasoning tokens, tool loops, retries, the system prompt the harness adds). Label each cause Verified
    (you observed it in the run's facts; cite the file) or Inferred (state the model and what would confirm it).
    Cite only numbers that appear in the generated tables.
  - Regenerate with the analysis, and open it:
    `uv run bench report --cost-compare <RUN_ID> ... --out <OUT>/benchmark-comparison.html
     --analysis <OUT>/benchmark-comparison-analysis.md --open`
    A refusal lists the numbers that do not appear in the tables: fix the analysis, never the tables.

STEP 6 - page 3, pack-on vs pack-off (for tuning the AI-Forward pack)
  - Generate: `uv run bench report --pack-cost <RUN_ID> ... --out <OUT>/pack-on-vs-off.html`
  - Read its tables: per harness, the extra tokens of the pack-on arm over the pack-off arm, split by where they go
    (instructions and skills loaded into the prompt, extra requests, extra tool calls, extra reasoning, cache
    misses), and the quality difference per task.
  - Read the pack itself at the run's pack revision (C:/Projects/ai-forward at the commit in handoff.json; read
    with `git -C C:/Projects/ai-forward show <commit>:<path>`, never check it out): the always-loaded files, the
    skills the cells invoked (runs/<RUN_ID>/harness_events), and their sizes.
  - Write <OUT>/pack-on-vs-off-analysis.md:
    (a) per harness, where the extra tokens come from, largest first, with the pack file or behaviour that causes
        each (Verified or Inferred, as in STEP 5);
    (b) where the pack paid for itself (grade gains) and where it cost tokens with no grade gain;
    (c) tuning candidates, ranked by expected token saving, each with: the change (a file, a section, a load rule),
        the evidence, the expected effect, the risk to quality, and how a next run would measure it.
    Cite only numbers that appear in the generated tables.
  - Regenerate with the analysis, and open it:
    `uv run bench report --pack-cost <RUN_ID> ... --out <OUT>/pack-on-vs-off.html
     --analysis <OUT>/pack-on-vs-off-analysis.md --open`

STEP 7 - close
  - `git add <OUT>` and commit: "docs(benchmark): grading and reports <REPORT_ID>". Do not commit runs/ (it is

Known caveats (say so in the pages where they apply):
  - Grok runs one cell at a time and is slow; its wall time is not comparable to parallel harnesses per run, only
    per cell.
  - Antigravity (agy) does not report its context window; its served context is "not recorded".
  - Copilot's per-request rows come from its debug log; where that is missing the page says "not recorded".
  - Claude Code's 1M window is judged from the adapter's final usage update (Ruling 123); in-turn 200000 values are
    a seed, not a measurement.
  - The pack page converts prompt characters to tokens per cell (first-request input / prefix characters). For
    Copilot this overstates the pack's share, because its tool catalogue is in the input but not in the counted
    prefix. Keep that split labelled Inferred; the fix (use the off/on pair's first-request difference) is owed.
  - A run with fewer than 2 repetitions per cell has no spread; say so rather than draw a conclusion from one cell.
