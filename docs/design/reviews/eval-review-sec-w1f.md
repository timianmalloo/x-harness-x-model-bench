### Checks that held (no finding)

- Credentials never reach a grading or check process: the environment is an allowlist built once in `_env.py` and used by the hidden-test phase, the check, the probe host and the build. `HB_CLAUDE_OAUTH_TOKEN` is on `denied()` and on the existing `DROP_EXACT`. Residual, not new: on a dotnet task `USERPROFILE` and `APPDATA` are in `DOTNET_HOST_ENV`, so same-user agent code can read the operator's credential files by path. That is ADR-0013's accepted same-user model; the check itself is declared with toolchain names only for the tasks that need them.
- Job-alone: the check and `spawn_deliverable` use `sys._base_executable` with `DETACHED_PROCESS`, as `docs/notes/spike-e1-job-alone.md` requires (alone only holds there, Verified in that note). `procs.spawn(console=False)` and `test_spawn_console_false_is_detached_and_job_holds_only_the_child` pin it. The job query failing reads as not alone. The probe host is also spawned through `spawn_deliverable`, so it is swept like any member.
- Hidden-test then check phase order, fresh copy, `check/` copied and hashed last; stdin closed on every path; the closed outcome set; the grader derives every derivable measure.
- STRIDE table: all ADR-0018 rows have a control, a test node and a disposition (A1 to A13), plus N1 to N9 for the reviews. A7 is a named transfer to X-LB, unreachable in E1. A3 and A5 state their residual honestly. The gaps are findings 2, 3 and 7 above (Repudiation and DoS rows show NA outcomes but not the verdict effect).

## W1-F rev 3 delta, 2026-10-03: `design/eval-property-grader-r3` at f125430a

PERSONA: security-identity-architect · MODE: Adversary · TIER: T2. Scope: section 5.5 (rewritten) and section 10 N12 to N14, against W0 rev 3 section 3. Read from the branch with `git show`. The SP-F3 scripts are not committed, so the 9/9 figures are Inferred (reported, not re-run). W0 and W1-F agree on frame names, app keys, start bound and app-output routing (compared line by line; no seam disagreement).

**Verdict on the three questions.**
- **Is the fd redirection a sound boundary on Windows?** Yes for what it is for; no as a forgery boundary against deliberate code. (a) The check's own result pipe is never in the host's inherited handle list (`close_fds=True`, explicit stdio, G8), so no redirect is needed to protect it. (b) The private protocol copies come from `os.dup`, which is non-inheritable (PEP 446), so a grandchild cannot hold the protocol pipe open. (c) After `dup2`, handles 0 to 2 are the NUL device and the app-output file: inheritable, but harmless. (d) `DETACHED_PROCESS` leaves no console, so `CONOUT$` has nothing to open, and a default-stdio grandchild gets no handle (G20: its output is lost, not rerouted). What it does not stop: same-process code can write to the private copies (fds 3, 4) and forge or consume frames. That only shapes the deliverable's own responses, which is what a probe measures, and the check decides every outcome. `OpenProcess` plus `DuplicateHandle` onto the check stays the ADR-0018 section 10a accepted residual (G8), unchanged. N13 should say so: the start sequence defeats module-body and factory forgery, not deliberate handle theft.
- **Can `{state_dir}` substitution be steered?** Not by the agent. The input is `args` from `cases.json` (the grader's copy of the hashed `cases.yaml`), replaced in one `str.replace` pass with the check's own path. Keys are untouched and there is no `format`, so no brace injection and no recursion. The remaining steering is through the filesystem, not the text (findings 2 and 3).
- **Is RF-11 acceptable for E1?** Yes, with a wording condition. A grandchild's output is lost (a false-negative direction for S1 `leak-2`, never a forged frame). E1 has one property task (S1) whose logging is in-process. An agent can already log to any file it likes, so `leak-2` was never tamper-proof; it measures accidental leakage. Say that in S1's `leak-2` text (finding 6).
