The problem

Today the portfolio measures SWE capability: can the agent make hidden tests pass on a small, fully specified task. On the smoke tasks, pack-off agents already pass 48 of 54 cells, and 5 of 6 tasks reach 100% pack-off. The AI-Forward pack claims something different. It claims to catch what a capable agent misses: a trust boundary, a piece of personal data, a flaky dependency, a follow-up change that punishes a short-sighted design, an API that changed since training. None of the 22 BOM tasks carries such a latent requirement with a mechanical oracle. So the benchmark cannot tell rigor that pays from ceremony that costs. This proposal adds that axis without turning the benchmark into a judge-driven essay contest.

Design rules for enterprise tasks

  1. Every task hides one latent requirement, and a mechanical oracle checks it. The prompt states the business ask the way a user would ("add a CSV export of orders"). It never states the enterprise constraint ("validate the tenant"). The constraint is discoverable from the repository: a policy doc, an ADR, an existing guard in a sibling handler, a data-classification file. This tests grounding, which is the pack's claim, rather than instruction following.
  2. Every family has a control variant with the constraint absent. Same ask, a repository with no trust boundary or no PII. The control measures false-positive ceremony: security theatre, unneeded retries, added layers. The pack's "aggressively simplify" intention is only testable against a control.
  3. Mechanical first; a judge only where no oracle can decide. Follow the catalog's oracle ladder (proof or model check → trace conformance → tests → judge). Use a judge only for artifacts a test cannot evaluate: a threat model's completeness, an ADR's rationale. Use two blind judges with a rubric, as bench/rubrics/ already does.
  4. Graded, not binary, where possible. "7 of 9 exploit probes blocked" carries more statistical power per cell than pass/fail.
  5. Brownfield and realistic size. Reuse the vendored ai-de and cfd-bench trees. Latent requirements need a codebase with conventions to be latent in.
  6. The deliverable location is part of the contract. Grade the named checkout. Record a separate validity code when the change exists elsewhere, so "delivered in the wrong place" is never confused with "wrong code".

Proposed task families

Letters continue the BOM's scenario scheme. Each family: 4 tasks (3 with the latent requirement, 1 control), in C# (ai-de) and Python, so all three harnesses face both.

H · Security by design

Example
"Add an endpoint that returns a tenant's evidence export." The repo has a tenant guard in sibling handlers and an ADR requiring it. Traps: IDOR, injection through a filter parameter, a secret written to a log.
Oracle
Hidden exploit probes (cross-tenant read, injection payloads, path traversal) run against the built service. A SAST delta on the diff (Semgrep with pinned rules, dotnet analyzers and Bandit). A secret scan (gitleaks-style patterns; the harness's egress scanner already has credential shapes).
Metrics
exploit_probes_blocked (ratio), sast_new_findings (count), secrets_in_diff (count), plus pass_at_1 for the functional ask.

I · Privacy and data governance

Example
"Log search queries so we can improve ranking." Fixtures carry seeded PII canaries (emails, national-id shapes), and the repo has a data-classification.md.
Oracle
Run the feature on canary fixtures, then scan logs, outputs, stored rows and captured outbound calls for canary values. The harness already plants and scans canaries for egress (report-record canaries), and this reuses that. Check that a retention or deletion field exists where the classification requires it.
Metrics
pii_canary_leaks (count), purpose_fields_present (ratio), third_party_egress_of_pii (count).

J · Compliance and auditability

Example
"Let an operator correct a ledger entry." Latent: an append-only correction with actor, before and after (the repo's ledger ADR); a reversible, expand-contract migration; new dependencies licence-compatible.
Oracle
Hidden tests assert an audit event with the required fields and no in-place update. Run the down-migration and a round trip. Check new dependencies against an SPDX allowlist.
Metrics
audit_event_coverage (ratio), destructive_updates (count), migration_reversible (binary), licence_violations (count).

K · Resilience

Example
"Fetch rates from the pricing service and cache them." The dependency is a harness-controlled fake that injects latency, 5xx, timeouts and duplicate deliveries.
Oracle
A fault suite with fixed seeds: the call has a timeout, retries are bounded and jittered, duplicates are idempotent, the cache has a bound and does not stampede. G1/G2-style formal checks where a protocol exists.
Metrics
fault_suite_pass (ratio), idempotency_violations (count), unbounded_resources (count), p99 latency under the injected fault profile.

L · Operability and observability

Example
"Add a background job that reconciles stale evidence." The repo's standard requires structured logs with trace ids, stable error codes and a health signal.
Oracle
Run with a file exporter and assert the telemetry contract: spans named, error codes from the registry, RFC 9457 error bodies on the HTTP surface.
Metrics
telemetry_contract_coverage (ratio), unregistered_error_codes (count).

M · Long-horizon change and cost of rework

Example
Two sessions on one repository. Session 1: "add multi-currency totals". Session 2, a fresh session with the session-1 tree: "support a second region with data residency". A short-sighted session 1 (a global static rate, region hard-coded) forces rewrites in session 2.
Oracle
Hidden tests at each step. Session-2 churn is computed against the session-1 tree.
Metrics
rework_ratio (session-2 lines changed in session-1 code ÷ session-1 lines added), tokens_to_green_total, wall_to_green_total, regressions_introduced. This family directly tests the claim "get it right first time rather than come back".

N · Unfamiliar or changed API (Spike Protocol)

Example
Use a vendored library pinned at a version released after the models' training cutoff, where one method was renamed and one default changed from safe to unsafe (for example, TLS verification or a retry default). The task compiles against the model's remembered API only by accident.
Oracle
Hidden behavioural tests on the changed semantics. The transcript is checked for a verification step (source read or minimal probe run) before first use.
Metrics
hallucinated_symbol_errors (build errors naming a non-existent member, counted from build logs), unsafe_default_used (binary), verified_before_use (binary, transcript-derived).

O · Simplicity under constraints (the anti-ceremony family)

Example
The control variants of H–L, plus tasks where over-engineering tempts: "make the timeout configurable", where the repo already has one config pattern.
Oracle
Diff statistics against a reference solution: product lines, new types, new dependencies, new config keys, cyclomatic complexity delta. Also: ceremony files written outside the blast radius.
Metrics
size_vs_reference (ratio), new_abstractions (count), new_dependencies (count), unrequested_infrastructure (count).

P · Drift and rat-holes

Example
A task whose repo has a tempting unrelated failure (a flaky unrelated test, a TODO in a touched file).
Oracle
Existing scope_creep, plus: was the side issue reported (a string match in the final message) rather than fixed.
Metrics
scope_creep, side_issue_reported (binary), delivered_in_named_checkout (binary).

Sample sizes for significance

grid-1 teaches two things. Cost effects are huge and consistent: token ratio above 1 in 51 of 54 pairs, so 10 pairs settle them. Quality effects are small against a saturated control, and n = 3 per cell detects only a 6-of-9 swing. For binary outcomes, a two-sided α = 0.05 test at 80% power needs about this many cells per arm (normal approximation to two proportions; the arithmetic is shown):

Cells per arm to detect a pass-rate difference
Pack-off rate → pack-on rateΔn per armWhat that means
0.50 → 0.800.30≈ 39one family (4 tasks × 5 reps × 2 combos = 40)
0.60 → 0.800.20≈ 81two families pooled, or one family × 4 combos
0.65 → 0.800.15≈ 138an intention-level verdict pooled across H–L

n = (1.96·√(2p̄q̄) + 0.8416·√(p₁q₁ + p₂q₂))² / Δ². Example: 0.50 → 0.80 gives p̄ = 0.65, (1.322 + 0.539)² / 0.09 ≈ 38.5.

  • Design the tasks so the control arm sits near 50%. A latent requirement that pack-off agents already meet 100% of the time (the grid-1 situation) cannot show any gain. Calibrate each task in a pilot of 5 pack-off cells and drop or harden tasks outside 20–80%.
  • Prefer graded metrics (probes blocked, leak counts). A per-task paired bootstrap on a ratio metric needs roughly half the cells of a binary one at the same effect. INFERRED: a rule of thumb that depends on the metric's variance, to be checked in the pilot.
  • Pair by task and repetition, and cluster by task. The board's existing paired bootstrap (stats.paired_delta, by task) is the right estimator. Add a McNemar count per family for the report.
  • Five repetitions, not three. Five gives the per-task direction a chance. Three only suits the smoke ring.

Rollout

  1. Phase 0: fix measurement (before any new task). Add a price list for every served model. Add a validity code for a deliverable outside the named checkout, and grade the diverted tree as a secondary score. Fix the A1 matcher (it matched none of three near-verbatim key questions). Record the judge metrics, or remove them from the catalog's weights until they are recorded. Fix the B1 heading check, which fails both arms for layout. Ship the pack-improvement report section (spec).
  2. Phase 1: three families (H security, K resilience, M rework), 4 tasks each, pilot-calibrated. These three test the pack's most expensive claims: designed-in security, resilience, and right-first-time.
  3. Phase 2: I, J, N, O. O's control variants reuse H–L repositories, so they cost little to author.
  4. Phase 3: L, P, and the ring split. One task per family goes into the smoke ring (every pack revision); the full families run at pack release.

Cost estimate INFERRED from grid-1's measured means (pack-on about 3.9 min and 1.4 M tokens per cell): one family at 4 tasks × 5 reps × 2 packs × 3 combos is 120 cells, about 8 agent-hours and 100–170 M tokens. Brownfield tasks will run longer than the smoke tasks; the pilot measures this.

Risks and how they are contained

  • Teaching to the test. The pack could add "check for tenant guards" rules. Contain: the latent requirement is found by grounding in repo evidence, and it varies by task. Held-out families are not published to the pack authors until after a pack revision is measured.
  • Judge creep. Contain: the metric table is mechanical except for one judge row. New judge metrics need a written reason that no oracle rung can decide the property.
  • Enterprise tasks that reward complexity. Contain: every family has a control, and family O penalises unrequested infrastructure, so heavy-handedness costs points.
  • Contamination. Contain: authored tasks on vendored private-history trees, and post-cutoff library versions for N. CONTAMINATION_PRONE exclusion continues for public-benchmark tasks.
