Lean runs of 2026-10-13: what they show, what broke, what changed

Update 2026-10-14. Three facts found since change how these runs read (details and fixes in
docs/plans/benchmark-instrumentation-2026-10-14.md): (1) Copilot's pack-on cells ran none of the pack's hooks,
because copilot -p runs repo hooks only in a trusted folder and cells were not trusted (verified by spike; fixed,
W17); (2) Copilot's per-call ok meant "the tool ran", so a failing shell command counted as a success (fixed, W14);
(3) Codex tool-phase, re-read and pack-cost numbers that went through cell_trace were doubled (fixed, W4). Grok
finished: 60/60, 58 valid, 1 cell lost to the Grok CLI's 10-hour cap on background tasks, 1 false out-of-profile flag
(fixed, W18).

In one minute

  • Copilot vs Codex, same model (gpt-6.1-sol). In the 60 headless cells, Copilot does more: 3.6x the tool calls,

3.4x the reasoning tokens, and it changes lines outside the task (median 16.5 discretionary lines; Codex 0). That is behaviour, not only output style. In the interactive sessions you watched, the opposite: Codex polled 10x too often, wrote 10x the text and skipped the last three steps; Copilot followed the prompt. Two confounds keep this from being a clean harness verdict (section 2), and the instrumentation to remove them is listed.

  • What broke. 18 issues. 12 are fixed in this change, tested, merged and pushed. 6 need your decision (section 3).

The biggest: bench report failed on every run; the early validity check could never fire; every Codex cell was invalid because the bench's Codex profile was out of date; a resumed Grok run could write a live token into the repo root.

  • Bench and grading. Keep capture and the deterministic checks with the run, and make them per cell; keep model

judging and analysis separate (section 5).

  • Prompt 2 is now "analyse the lean runs": it finds finished runs itself, never copies them, judges only on request,

and writes four pages, including a behaviour page for exactly your question (section 6).

  • Grok takes about 18 hours because it runs one cell at a time and spends 67% of each cell reasoning; the pack's

hooks add about 5 minutes per pack-on cell. A login pool now lets it run in parallel (section 4).

4. Why Grok takes about 18 hours

Measured on its first 5 cells, from Grok's own events:

  • One cell at a time. 60 cells x 14-22 minutes. The cap exists because a Grok login rotates its refresh token, so

cells cannot each copy it. Fixed by the login pool (B8): with N homes, N cells run at once.

  • Reasoning dominates. 61.3 of 91 measured minutes (67%) are spent streaming reasoning, over ~28 model requests

per cell. Time to first token is ~4 s, so this is reasoning volume, not latency (B14).

  • The pack's hooks. Pack-on cells spend 4.6-6.0 minutes in tools against 0.2-0.9 pack-off: file reads take a

median 11 s and edits 18 s because three hook processes run before each call (B15/P1). That biases pack-on vs off time comparisons against the pack.

5. Should bench and grading be coupled?

Recommendation: split by what the step is, not by name. Three layers:

  1. Capture and deterministic checks belong with the run, per cell. Today bench run already ends with a

deterministic grading pass (cli.py:428, no judge calls), but it runs once, at the end. That is why the early check could not work and Codex ran 60 invalid cells. Move fact extraction and validity to each cell's end (the engine already reads each cell's record), and let status show them live. --check-ended is the first step.

  1. Model judging stays separate and optional. It costs tokens, is non-deterministic, and must be re-runnable

on frozen archives (the verdict store). Prompt 2 now judges only when asked.

  1. Analysis and reporting stay separate. They are pure functions over the facts, cross-run, and change more often

than the runs (this whole drift analysis needed no re-run). The bench report failure is the cautionary example: a report that assumed a run shape broke every run.

6. How the analysis prompt (Prompt 2) changed

  • Finds every finished run itself (READY / LIVE / BROKEN); live runs are listed as pending, not waited for.
  • Never copies runs: it reaches them through directory junctions (verified to work with bench verify and status).
  • Model judges only with JUDGE = yes.
  • Four pages: run health and issues (including each CLI session's own problems, from its transcript); behaviour

(drift, ceremony, over-thinking, the same model in two harnesses, both layers); cost; pack on vs off.
