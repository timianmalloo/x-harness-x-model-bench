# Defect-class register

*Governed by `continuous-improvement.md` (CI1–CI12). **One entry per class, not per bug.** A new occurrence of an existing class appends to that class's Instances and triggers a control review. Read this at grounding (CI5) for the area you are working in.*

**How to use this file**
1. On any defect, correction, or falsified assumption, answer **class → sweep → derive → prevent** in writing (CI2).
2. Find the matching class below, or add one. Append the instance.
3. Climb the control ladder (CI6) and record the highest rung that actually holds: *make it impossible* > *automated control* > *always-loaded instruction* > *knowledge doc* > *register entry only*.
4. A control is not a control until it has been **observed failing** on the un-fixed code.

## Project classes

### MOD-A — A seeded model variant that cannot fail, or fails for the wrong reason
- **Signature:** a seeded-bug variant of a TLA+ model reports `NOT rejected`, or is rejected by an invariant other than the one it targets. The model looks verified; the targeted invariant proves nothing.
- **Why it survives:** the real design passes, so the model looks correct. TLC stops at the first violation, so a variant caught by the *wrong* invariant still prints "violated". A later fix (a new invariant, a new guard) can silently change which invariant catches an older variant.
- **Instances:**
  - `2026-09-23` design gate round 2 — the new `NoOutcomeWhileRunning` pre-empted `launch_after_outcome` and `reconcile_no_wait`; both still showed "violated", but not by their targets.
  - `2026-09-23` model v2 — `archive_live` made vacuous by the kill → record fix; `ignore_orphans` vacuous (replaced by `NoLaunchBesideOrphan`).
  - `2026-09-23` model v1/v2 — a guard reading a history variable (`prompts = 0`) hid `relaunch_prompted` twice.
  - `2026-09-23` model v1 — two guards for one invariant masked `exceed_parallelism`.
  - `2026-09-25` R-75 mutation seed (Grok worker; caught by the Leader at the join) — the red-baseline seed's always-failing test never called `Compute`, so it covered no mutant and could not show whether Stryker kills with an initially failing test; its name check compared `killedBy` test **ids** with a test **name**, so it could not fail either. Fixed: the failing test calls `Compute`, the seed asserts at least one `Survived` and no `Killed`, and killer ids are mapped to names through `testFiles`. The general shape: a seed must assert its own precondition (here, coverage) or it proves nothing.
- **Sweep:** all 22 variants re-run after the isolation change; every one is rejected by its own target. 2026-09-25: the other `not in str(...)` absence checks in `tests/` (`test_egress.py:283`, `test_report.py:300`) compare text with text and can fail.
- **Control:** `tools/check_models.py` checks each safety variant against its target invariant alone (`only_invariant`) and each liveness variant against its target property alone (`only_property`), asserting the target's name in TLC's output. `tests/test_check_models.py::test_every_checked_property_has_a_seeded_variant` (observed failing when a variant was removed, 2026-09-23) and `test_variant_config_checks_only_its_target`. Guards never read history variables (stated in the model design).
- **Status:** `controlled`

### EDIT-A — A blanket text replacement renames more than the target
- **Signature:** a mechanical rename (`AllCells` → `Cells`) also rewrites identifiers that contain the target (`NotAllCellsFinished` became `NotCellsFinished`).
- **Why it survives:** the replacement looks local; the collateral hits are in other identifiers.
- **Instances:**
  - `2026-09-23` removing the coordinator from the model broke the witness invariant's name. `check_models.py` failed closed ("not defined in the specification"), and the name was fixed before the commit.
- **Control:** renames use whole-word matching (`\b…\b`, as the later `container` → `proc` rename did). `check_models.py` fails on any undefined invariant, and `test_every_seeded_variant_targets_a_declared_property` checks the names. Observed failing, 2026-09-23.
- **Status:** `controlled`

### EDIT-B — Escape sequences corrupted by nested string generation
- **Signature:** code or data written by a script that is itself inside a shell heredoc or a string literal. A `\n`, `\\` or `\\?\` in the intended text arrives as a real newline, a single backslash or a lost prefix.
- **Why it survives:** the generating script runs without error; the damage shows only when the written file is parsed or run later.
- **Instances:**
  - `2026-09-23` `tests/fake_acp_agent.py`: `"\n"` became a line break, so every engine test failed.
  - `2026-09-23` `tests/mutations/engine.json`: `\n` inside JSON strings became line breaks, making the JSON invalid.
  - `2026-09-23` the fixture scrubber: a `\\?\` long-path prefix lost a backslash.
  - `2026-09-23` `tests/test_grade.py`: the class recurred after it was registered. A heredoc edit script's `\\n` arrived as a line break, and the script's own `assert` stopped it before any write. The prose control had not held.
  - `2026-10-04` X-E (`build/eval-x-e`, reported by X-E): a heredoc mangled backslashes. The file and the shell form are not recorded here. The hook blocks only a heredoc fed to a Python interpreter, so a heredoc that writes a file (`cat > f <<EOF`) is outside it: a gap to check on the next instance.
- **Control:** `tools/heredoc_guard.py`, a `PreToolUse` hook on Bash wired in `.claude/settings.json`. It blocks (exit 2) any heredoc fed to a Python interpreter, so a program is written to a file and then run (CT27), and code is changed with the Edit tool. `tests/test_heredoc_guard.py` pins the blocked and the allowed shapes; it was observed red before the guard existed. The suite still fails at once on an unparseable module.
- **Status:** `controlled` (2026-09-23)

### INS-A — Progress hidden by buffered output
- **Signature:** a long check writes to a log file that stays empty until the process exits, so nobody can tell which stage is slow or hung.
- **Why it survives:** on a terminal, output is line-buffered and looks fine; redirected to a file, it is block-buffered.
- **Instances:**
  - `2026-09-23` `check_models.py` redirected to a log: 10 minutes with an empty log and TLC at 43 GB; the run was stopped blind.
- **Control:** every result line in `check_models.py` prints with `flush=True`. `NONE YET` as a test; the upgrade trigger is a second instance in another script.
- **Status:** `partially-controlled`

### CONC-A: check-then-act on a shared destination under concurrency
- **Signature:** two workers each check "does `dest` exist", both see no, and both build and publish into it. On Windows, `os.replace` onto a non-empty folder fails with `WinError 5`.
- **Why it survives:**
  - Unit tests build one cell at a time.
  - The race needs two cells that share a content-addressed input, running in parallel.
  - The first real E2E was the first run with both.
- **Instances:**
  - `2026-09-24`, first real E2E: `workspace.task_source` and `workspace.pack_checkout` raised HB-CELL-113 for the second `pack=on` cell (T6).
- **Sweep:** `grep os.replace|.rename(|shutil.move` over `src` finds one site, `workspace._land`, which both functions now use. `cell_working_copy` has a per-cell `dest`, so nothing shares it.
- **Control:** `tests/test_workspace.py`'s two concurrency tests use a `threading.Barrier`. They were observed red at `0082875` (re-run by the Coordinator). The two `tests/mutations/workspace.json` mutants are killed.
- **Status:** `controlled` (2026-09-24)

### PATH-A: a relative path handed to a subprocess that runs in another folder
- **Signature:** a path argument stays relative, and a subprocess started with `cwd=<some other folder>` resolves it there. The file "does not exist".
- **Why it survives:** tests pass absolute paths (`tmp_path`, `ROOT / ...`). Only an operator typing a relative path hits it.
- **Instances:**
  - `2026-09-24`: `bench --tools-dir .tools/harness run` looked for `pack-apply.py` under the cell's working copy, which gave HB-CELL-113 (T8-2).
  - `2026-09-25`, the repo-local `PreToolUse:Bash` hook in `.claude/settings.json` ran `tools/heredoc_guard.py` relative to the session's cwd. The Leader ran `cd .git/coord-runs/qualify-7`, the cwd stuck, and every Bash call was then refused ("can't open file …\qualify-7\tools\heredoc_guard.py"). The fix anchors the path at `${CLAUDE_PROJECT_DIR:-.}`: run from `C:\` with the variable set, it still refused a Python heredoc (exit 2) and allowed `ls`. Unset, it falls back to the old relative path. `assume:` Claude Code sets `CLAUDE_PROJECT_DIR` for hook commands. It is not set in the Bash tool's own shell. Confirm by one Bash call from a cwd outside the root after the next session start. If it is false, the hook falls back and fails the same way from outside the root.
- **Sweep:** every CLI path argument (`--root`, `--runs`, `--cells-root`, `--tools-dir`, `--pack-source`, `--matrix`) is resolved once in `cli._resolve_paths`. `grep add_argument` lists no other path argument. Every `cwd=` site in `src` takes a path derived from those.
- **Control:** `tests/test_cli.py::test_a_relative_tools_dir_resolves_absolute_and_the_pack_on_build_succeeds`, observed red at `62c38ba`. The `t8.json` T8-2 mutant is killed.

### TOOL-A: an in-place mutation leaves stale bytecode

### ORCL-A: an oracle proven against a working copy the engine never builds

### ORCL-B: an oracle's behaviour depends on the grading copy's location, because a tool inside it discovers configuration upward
- **Signature:** sibling of ORCL-A (also a proof/grading-environment mismatch), different mechanism: the working copy itself is built correctly (the engine's own `shutil.copytree`/`git archive`, not a hand-rolled clone), but *where* it sits changes what an oracle command run inside it sees. Not `--no-project` missing from `task.yaml` (that flag papers over the location, it does not fix it); the defect is that a grading copy's location was never guaranteed to be free of ancestor project files at all.
- **Why it survives:** the failure is silent success, not a crash: an authoring-time proof (run from wherever the author happened to be, invariably outside the repo) shows the oracle discriminates correctly, `bench validate`/`oracle/evidence.md` accept it, and the divergence only appears once the *engine* grades a real run from its own `runs/<run>/grading/...` path -- an environment authoring-time testing never reaches.
- **Instances:**

E1's command carries `--no-project` and graded fine, and E6 (`dotnet`) is unaffected (no `global.json`/`Directory.Build.props`/`NuGet.config` above `runs/`, checked).
- **Sweep (which upward-discovering tools could reach the repository from a grading or cell working copy, checked 2026-09-30):**
  - `uv`/`pip` (`pyproject.toml`, `.python-version`, `pip.conf`/`pip.ini` via `PIP_CONFIG_FILE` search) -- **affected**, the measured instance.

- **Control:** every grader's disposable working copy (`grade/_changes.py`'s `pre_turn_tree`/`grading_copy`, `grade/formal.py`'s `_grading_copy`) now lands under `cells_root/grading/...` (`CellInput.work_root`), never under `run_dir` -- outside every project, by the same argument ADR-0013 already makes for cells (see ADR-0013 Amendment 2, `docs/adr/0013-native-cells-own-working-copy.md`). `grade/runner.run_pass` refuses (`HB-GRD-006`, `workspace.check_grading_root`) a grading root with a `pyproject.toml`/`.python-version` in it or any ancestor, so a future misconfiguration fails loudly at grading time instead of silently rebuilding the engine's own environment. `tests/test_grade_correctness.py::test_a_grading_copy_nested_in_a_dummy_project_still_runs_uv_standalone` reproduces the defect against a fixture dummy project (skips without `uv`) and asserts the dummy project's own `.venv` is never created.

### PLAT-A: a Windows-only assumption invisible until a second real platform runs the same code

Nothing about the code looks wrong: it is an ordinary sort call, a temp-dir join, a subprocess close.
- **Why it survives:** a single-platform CI matrix proves nothing about the platform it never runs. Every shape here passed review and every test on the one host that ever ran it. ### CAUSE-A: a classifier's default bucket silently absorbs an unmatched case and widens its containment scope
- **Signature:** a function that maps evidence (a status, an error type, free text) to one of several named outcomes has a final `else` / fall-through case whose name looks like "we don't know" but whose downstream behaviour is specific and consequential — here, `model_unavailable` reads as "the plan pinned a model the account cannot serve" (a `benchmark` attribution) but a default hit actually meant "this classifier has no rule for this evidence". The bug is invisible at the call site: the function always returns *something* of the right type, so nothing raises, nothing NA's, and no test fails — only the thing it silently routed to is wrong.
- **Why it survives:** a named enum member reads as a real, intentional classification rather than "nothing else matched", so a reviewer sees `Cause.model_unavailable` and reads a deliberate decision, not a miss. The two real cases this default was built for (a genuinely unservable model, a genuinely unmapped status) are common in fixtures; the cases it silently absorbs (a status-less auth failure, a status-less network failure) are rare enough that the golden fixtures never exercised them, so the default looked correct for months.
- **Instances:**
  - `2026-09-30` (CAUSE-A, `normalize.classify`): grid-2's cc-opus row (an `isApiErrorMessage` row with no `apiErrorStatus`, `error: "authentication_failed"`) and copilot-sol row (a `session.error` with no status, a DNS/ENOTFOUND message) both fell through every rule to `Cause.model_unavailable`. `model_unavailable` opens a **combo-scoped** `qualification_gap` decision (`engine.DECISION_CAUSES`), so both silently skipped their whole combos (72 + 55 cells) instead of `blocked_auth` (harness-scoped `blocked_cell`, PE-4) or `Cause.provider` (infrastructure, never opens a decision that stops launching). The two real containment scopes the default was meant to catch (run-wide auth block, combo-wide unservable model) are both narrower or differently-scoped than "silently skip 127 cells project-wide"; the default bucket changed *what the system did*, not just how the cell was labelled.
  - The same shape existed a second time in the same file before this fix: `driver._auth_failure` and `normalize.classify` each independently decided "is this text an auth failure", so a status-less auth failure reached `blocked_auth` on the driver's prompt-time path but `model_unavailable` on the native-record scan path for the identical underlying wording — two definitions of one classification (DM-A's cause-domain sibling), fixed by moving the rule to one place (`normalize.is_auth_failure`) both paths call.
- **Sweep (2026-09-30):** every function in `src/` returning `Cause` (`normalize.classify`, `driver._prompt_error_cause`, `engine.Engine._classify`) and every `.get(name, <default>)`-shaped classifier (`TOOL_CLASSES`/`TOOL_CLASS`/`MCP_CLASSES` mapping an unrecognized tool name to `"other"`, `codex._tool_class`'s same fallback, `error_type` readers defaulting to `"unknown"` in `claude_code.py`/`copilot.py`/`codex.py`). Findings:
  - `engine.Engine._classify`'s own final fallback, `Cause.adapter_crash`, is **not** an instance: it is reached only after every more specific rule (native-record scan, kill reason, memory signature, driver cause, a completed stop reason) has been checked and declined, it is exercised by an explicit parametrized precedence table (`tests/test_engine.py::test_classify_applies_the_cause_precedence_in_order`), and `adapter_crash` genuinely means "the adapter ended without a cause we could name" — the honest case this pattern is for.
  - `engine.py:589`/`:885`'s `Cause.disk if _disk_full(exc) else Cause.unclassified` is the **correct** shape of this same choice: a real catch-all, but one whose name (`unclassified`, attribution `none`) says exactly that it is one, so nothing downstream reads it as a specific diagnosis. Contrast with `model_unavailable`, whose name reads as specific even when it was not decided by anything specific.
  - `TOOL_CLASSES.get(name, "other")` and siblings are a **different, correctly-built pattern**: an unrecognized tool name is meant to fail closed (R-34/R-35, `views._outside`, HB-VAL-008 out-of-profile), so landing in `"other"` widens validity checking, never narrows it — the opposite direction from this class.
  - The `"unknown"` fallback for a missing `error_type` field is inert on its own: `normalize.classify` only ever matches it against `PROVIDER_TYPES` substrings, never treats its literal absence as a decision, so it cannot by itself silently pick a scope-changing cause.
- **Derive (the general rule, CI2):** a classifier's default case is safe only when (a) its name says "unclassified"/"unknown", never a specific-sounding outcome, or (b) every prior rule is proven exhaustive over the evidence the classifier can see (never true for free text from an external CLI). A status-less failure is evidence the classifier has *less* information, not evidence for a *more* specific conclusion — text rules (auth, network) must run before the default, not be absent from it.
- **Control:** `tests/test_telemetry.py`'s `test_grid2_*` and `test_other_status_less_*` tests pin the two evidenced text rules directly to archived grid-2 rows (so a regression is a red fixture, not a review reads); `test_a_status_still_decides_first_even_with_auth_or_network_words_in_the_text` pins that a status still wins over text, so the fix cannot itself become a new default-swallows-everything rule the other direction.
- **Open residual (2026-10-03, architect council, SRE R4):** `blocked_auth` now classifies correctly, but its *attribution* field still reads `harness`, so the ordinary (non-campaign) board and pack section still score an auth-expired cell as a harness failure. The evaluation campaign keys off the named cause, not the attribution (ADR-0021 failure-modes table), so campaign verdicts are unaffected. Backlog: move `blocked_auth`'s attribution to infrastructure under a catalog bump (historical reports must not move silently, US-4), with a red-first board test on an auth-expired fixture cell.
- **Status:** `observed` (one recurrence fixed at discovery; no automated sweep yet catches a *new* scope-changing default being added elsewhere — the derive rule above is currently enforced by this register and code review only)

### GLD-A: a golden pinned from the implementation's own output inherits its bugs
- **Signature:** a golden/characterization test's expected values (counts, evidence-id sets, headline numbers) are set by running the code once against real data and copying what it printed, rather than by independently re-deriving each value from the underlying facts. The test then proves only "the code still agrees with itself" — a bug present at pinning time becomes part of the fixture forever, invisible to any change that preserves it, and a later *fix* to that bug shows up as a test failure that looks like a regression.
- **Why it survives:** the golden reads green from the day it is written (it was built from that exact run), review sees "matches the archive" and moves on, and nothing in the test or its docstring distinguishes "independently verified" from "copied from the tool's own first run." The tell is a golden whose docstring says what the numbers are but not how each was checked against something other than the code under test.
- **Instances:** `2026-09-30`, this branch (Leader forensic review, session `worker-sonnet-pi`): `tests/test_pack_improvement_golden.py`'s PI-T15 golden pinned PK-02's grid-1 count at 9 and grid-1-cc's at 5 from `report.pack_improvement.assemble()`'s own pre-fix output, at a time when `classify()`'s `product_write` rule could not match a native record's absolute paths against a relative `blast_radius` glob (see the `_relative_to_root` fix in the same commit). The golden's own count was therefore a photograph of the bug, not a fact about the archive: fixing the path bug moved grid-1's true count to 7 (not 9, and not the join's own hypothesized 5 either — two of the four false-positive cells turned out to be independently, genuinely `diverted_and_failed` too) and grid-1-cc's to 0 (the finding disappears entirely). Neither new number was guessed or copied from the fixed code's output either: each was cross-checked by temporarily checking out the pre-fix module (`git checkout 418f9ff -- src/harness_bench/report/pack_improvement.py src/harness_bench/telemetry/__init__.py`, restored after) and diffing the per-cell `stopped_without_product`/`diverted_and_failed` values against the post-fix run, cell by cell.
- **Sweep:** every other `-m gate` archived-run golden in this repo (`test_archived_runs_helper.py`, `test_check_regrade.py`, `test_grade_architecture.py`, `test_grade_correctness.py`, `test_grade_drift.py`, `test_grade_mutation.py`, `test_grade_rigor.py`, `test_grade_runner.py`) and `grade/drift.py`'s own `_in_radius` blast-radius matcher (PK-03's upstream source): `_in_radius`'s `path` comes from `_changes.change_set(base, work)`, a two-tree diff whose keys are already relative to those tree roots — a structurally different path source from a native record's own absolute tool-call arguments, so it was never exposed to this specific bug shape. No other golden in this sweep asserts a count or evidence-id set that depends on `classify()` or `_matches_blast_radius`.
- **Control:** a golden's docstring records, for each pinned number, what independently confirms it — read the writer's own format (as `pack_files_written`'s docstring already did for PK-03's drift.log line shape), diff a pre-fix vs post-fix run cell by cell (as this fix's PI-T15 docstring now does), or cite an external, non-generated source. A PR touching a golden's expected values without adding or updating that provenance is a review finding under this class, not a passing diff. Not yet a lint rule (a docstring's prose cannot be mechanically checked); upgrade trigger: a second instance, then a `pack-doctor`-style check that a `-m gate` test file's docstring names a verification method other than "matches the current run."
- **Status:** `controlled`

### GOLD-A: a code-identity field inside a result golden's bytes
- **Signature:** a canonical result export carries a field whose value is a hash of the *code* that produced the result (a grader's build hash, a normaliser's build hash), not a fact about the result itself. A byte-identity control (US-4/US-26's shape: "the export is unchanged under one catalog version, or across a re-grade") then fails every time that code is fixed, even when the fix moves no score, reason, or statistic the field's owner can see.
- **Why it survives:** the field looks like ordinary provenance (it answers "which code produced this?"), so including it in the result bytes reads as thoroughness, not as a defect. The failure appears only the first time that code changes, which can be months after the field was added — by then the control's false positive looks like the control doing its job.
- **Instances:**
  - `2026-09-30` (DR-CAT-1, R-86): `extraction_id` (the normaliser's build hash, `normalize.py:85`) sat in `views.export`'s per-cell bytes beside `grading_id` (already correctly excluded). A normaliser fix (R-15/R-24/R-54 provenance tracking) changes `extraction_id` on every re-grade, which the US-4 catalog control and the 0.3 byte-identity gate both read as "a score or reason moved without a bump" — a false positive with a real cost (it forces an illegitimate catalog bump or a forbidden re-pin). `grader_build` (the grader's own code hash) was already correctly kept out of the export; `extraction_id` was its unflagged twin.
- **Sweep (2026-09-30):** every committed export/golden fixture grepped for `grader_build`, `grading_id`, `extraction_id`: `tests/fixtures/catalog/{0.4,0.5}/*.export` and `tests/fixtures/validity/golden-exports-5feece0.json` carry `extraction_id` from before this fix — left untouched as frozen, point-in-time goldens for retired catalog versions (the established pattern: `leaderboard`'s R-78 removal did not rewrite 0.4's goldens either; a frozen golden is never re-validated against live code after its version is retired). `tests/fixtures/ledger/r34-cc-opus-pack-on-powershell-denied.json`'s `extraction_id` is a native-record/ledger-row fixture (`test_allowlist_classes.py`), not an export golden, and is unaffected. The one *current* consumer, `tests/test_views.py`'s pre-R-15 golden-export comparison, now strips `extraction_id` from the historical fixture before comparing, the same way it already strips `leaderboard`.
- **Control:** `tests/test_catalog_version.py::test_a_normaliser_change_alone_leaves_the_control_green_and_extraction_id_out_of_the_export` monkeypatches the code-identity source and asserts both that the US-4 control stays green and that the field is absent from `views.export`'s cells. Observed red before the fix (the (a) export-mismatch finding fired on the monkeypatch alone). The general rule (CI2 derive): a code-identity field (a build hash, a tool-version hash) never enters a result golden's bytes; it belongs in the row that already carries the pass's identity (here, `RunView.Cell.extraction_id`, read by `pack_improvement.py:887` and `context_growth.py:147` from the view object, never from the export bytes).
- **Status:** `controlled`

### GATE-D: a freeze control's pair check can only be satisfied by bumping the version it is not about
- **Signature:** a control gates two independently-versioned artifacts as a pair — here, a metrics catalog version `v` and an export-shape version `N` — by requiring one map to record `{N: {catalog: v}}`. Because that map holds exactly one `catalog` per `N`, a legitimate bump of `v` alone (no change to `N`'s shape) can only pass by rewriting an already-committed entry, which the control's own append-only rule ((e)) forbids. The control is unsatisfiable by construction for the exact class of change it exists to allow.
- **Why it survives:** the pair check was built and tested against the one case that exercises it going forward (an `N` bump under an existing `v`), never against the orthogonal case (a `v` bump under an existing `N`), because no catalog version had bumped since the export-shape pairing was added. The gap is invisible until the first bump arrives.
- **Instances:**
  - `2026-09-30` (DR-CAT-1, R-86): `test_catalog_version.py`'s (d) check required `board_exports[N].catalog == v`; `board_exports['3'].catalog` was pinned `'0.5'` with `EXPORT_VERSION` fixed at `3`, so a `0.6` freeze under the unchanged export version `3` could never satisfy (d) without editing `board_exports['3']`, which (e) then fails as an edited append-only entry. Found by reading the control against the version it was about to receive (R-81's "re-coupled the moment the first fix arrived" shape), not by running it.
- **Sweep:** the ruling's fix (`versions[v].board_export_version` recording the pair from the *version* side, append-only, with the per-version golden directory already in use for that version's own board digest) is the only pair-keyed check in this control; no sibling pair check exists elsewhere in the catalog or regrade controls (`check_regrade.py`'s criteria read single-sided baselines, not a two-key map).
- **Control:** `tests/test_catalog_version.py::test_a_catalog_bump_under_an_unchanged_export_version_pins_via_board_export_version_and_passes` (a `v` bump under a fixed `N` must pass) and `test_a_catalog_bump_with_no_board_export_version_fails_d_naming_both_maps` (without the pinning key, (d) fails and names both maps it checked). Observed red before the fix (the bump could not pass under any append-only freeze entry). The general rule (CI2 derive): a two-key pair gate records the pair from the side that is changing, append-only, never from a map keyed by the side that is staying fixed.
- **Status:** `controlled`

### BND-A: a fixed byte-size bound sized by intuition, not by measuring the real payload
- **Signature:** a protective bound on one message/line's byte size (a protocol reader's line cap, a record reader's line cap) is set to a round number (1 MiB) that reads as generous, with no measurement of what the real traffic actually carries. The bound then fires on legitimate, in-spec payloads — not malformed input, not a runaway stream — because the thing it is bounding (a tool result) can legitimately be larger than the guess. The failure mode is the opposite of what the bound exists to prevent: instead of containing a misbehaving adapter, it kills a cell that behaved correctly.
- **Why it survives:** the bound is qualified once, against small fixtures and short turns, where no real tool result is large enough to reach it (IO9: instrumentation over inference — the bound was reasoned about, never measured against production-shaped traffic). It then ships silently correct for months, because most tool results (text diffs, short command output) are far under 1 MiB; only a tool result with embedded binary data (a screenshot, an image read) or a verbose command's full stdout (`--verbosity detailed`) reaches it, and those are rare until the task mix includes them.
- **Instances:**
  - `2026-10-02`, grid-2/grid-3 (HB-CELL-107): `driver.py`'s `LineParser` (`MAX_LINE = 1 << 20`) failed 5 grid-3 cells (E3 cc-opus x4 across both reps and arms, D2 codex-sol pack-off r2) and 2 grid-2 cells (same cell ids, same task shape) on one oversized stdout line each. Measured from the archived native-record evidence (the best available proxy — the ACP wire line itself is never archived; `LineParser._too_long()` discards `self._buf` before any archive write, and for 2 of the 7 failed cells the archived native-record line measured *under* 1 MiB, meaning the true wire line was larger still, most likely because the native CLI process was killed before its own on-disk write of that in-flight message completed — a measurement gap named here, not modeled around): a Claude Code image `tool_result` (base64 PNG) ran 1.0–1.3 MiB; a Codex `CommandExecution`'s full `--verbosity detailed` dotnet-test stdout ran 2.3 MiB. Both are legitimate single tool-result payloads, not malformed input.
  - The identical `MAX_LINE = 1 << 20` constant, same value, same unmeasured origin, in `telemetry/__init__.py`'s `rows()` (the archived-record reader `claude_code.py`/`codex.py`/`copilot.py` all call) — a sibling instance of the same class, not a copy of the same bug: it degrades to `NOT_RECORDED` rather than failing a cell, but a cell that now survives the raised driver bound would still silently lose that row's token/tool-call data at grading time if this sibling bound were left alone.
- **Sweep (2026-10-02):** every other fixed byte/size bound in the engine, checked against the same archived evidence (grid-2, grid-3): `plan.py`'s `stderr_tail_bytes` (64 KiB) — measured max adapter-stderr-tail.log across the 5 grid-3 failures is 1,038 bytes, far under; `telemetry/__init__.py`'s `MAX_FILE` (256 MiB) — measured max native-record file size across those cells is 4.37 MiB, far under. Neither needed raising; the defect is specific to the *single-line* bound, not file-level or stream-tail bounds, because only a single tool-result's payload lands whole in one line. `grade/drift.py`'s own "a file over 1 MiB" trigger is a different mechanism (drift's own line-hash threshold on a *changed workspace file*, not an ACP/native-record line) and was not measured against this evidence — out of scope for this sweep, flagged for a future one if a drift false-fire is ever observed.
- **Control:** `driver.MAX_LINE` and `telemetry.MAX_LINE` raised together to 8 MiB (`8 << 20`) — a >3x margin over the largest directly measured line (2.3 MiB), bounded by `PHASE1_MAX_PARALLELISM` (4) so the worst case is 32 MiB of buffered line data, trivial against host memory. `tests/test_driver.py::test_a_line_within_the_measured_real_payload_range_is_not_a_protocol_failure` and `tests/test_telemetry.py::test_a_large_legitimate_line_within_the_raised_bound_is_not_skipped` (all three readers) pin a 2 MiB line as accepted; the existing oversized-line tests (`test_a_huge_line_is_a_protocol_failure`, `test_deeply_nested_and_huge_lines_are_skipped_as_malformed`, copilot's F10) were bumped past the new bound (10 MiB / 9 MiB) so they still exercise the too-long path rather than silently passing for the wrong reason. The general rule (CI2 derive): a byte-size bound on one message/line is sized from the largest *measured* real payload with a stated margin, never from an intuited round number — and a bound's sibling (the same cap value appearing in more than one reader for the same kind of content) is swept and raised together, or the half-fixed one becomes a new, quieter instance of this same class (NOT_RECORDED instead of a hard failure).

### HASH-A: a frozen contract value authored by hand-deriving the hash algorithm instead of calling the canonical function
- **Signature:** a task (or other frozen artifact) carries a pinned hash of some material (`formal.statement_hash`, a manifest digest, a golden's checksum) that a human- or agent-authoring step computed by reasoning through the hashing recipe by hand — a one-off script, a synthetic path label that is not a real file, a slightly different invocation of the underlying tool — rather than by calling the one function the real consumer (here, the grader) actually calls. The two computations can diverge on a detail the design left unspecified (here: one combined evidence file vs. one per declaration; `#check name` vs `#check @name`'s different Lean pretty-printer form) without either side being internally wrong, and the authoring doc may even flag the ambiguity and ask the implementer to "match this value exactly" — a request the implementer cannot mechanically honor when the authored recipe cannot be expressed through the project's one sanctioned hashing function at all (G12: a label containing `::` is not a legal Windows filename `plan.tree_hash` can hash a real `Path` for).
- **Why it survives:** authoring and implementing happen in different sessions, often different workers, with no shared executable contract between them — only prose (an oracle README's "S6" section) describing what the hash is supposed to cover. Both sides can pass their own review (the authoring evidence shows a real, reproducible manual computation; the grader's unit tests pin their own self-derived expected hash and so stay green forever) while disagreeing with each other. The mismatch is invisible until a real grading pass runs the frozen value against the real grader — by which point it fails identically on every cell that reaches it, which looks like "the agents all edited the statement" rather than "the fixture was never computable by the code that reads it."
- **Instances:**
  - `2026-10-01` (grid-3, grading `grade-20261001T210800-579e4f`): `tasks/G2/task.yaml`'s `formal.statement_hash` was computed per `oracle/README.md` S6's bespoke recipe (one synthetic hash entry per theorem name, labelled `Proofs/Statements.lean::<name>`, content from `#check @<name>`'s fully-explicit rendering). `grade/formal.py`'s `_statement_material` instead stages one combined `check.out` file (via `#check <name>`, no `@`) and hashes four real files through `plan.tree_hash`. Not yet a repo-wide lint (no mechanical way to detect "this value was hand-derived"); upgrade trigger: a second scenario-7-shaped task (or a non-formal frozen-hash contract) repeats this, then `new-bench-task`'s `status: ready` gate adds a mechanical check that a declared `*_hash` field reproduces under the one grader function it is paired with, wherever that function is pure and callable outside a live toolchain run.

### SCAN-A: an artifact scan treats a tool's own mandated build output as an agent-introduced violation
- **Signature:** a task's `prompt.md` requires the agent to run a build/test tool in a working directory before finishing (`lake build`, `dotnet build`, `pytest`); that tool unavoidably writes its own output into that same directory (`.lake/`, `lake-manifest.json`; `bin/`, `obj/`; `TestResults/`; `__pycache__/`).
