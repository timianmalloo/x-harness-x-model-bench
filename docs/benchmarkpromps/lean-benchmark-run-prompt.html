Prompt 1: run the lean benchmark for this CLI

Any CLI, any model. Nothing to fill in. The CLI you paste into works out what it is (harness, model, effort, context window) from its own configuration, names the run itself, and runs both arms: pack off and pack on. If the bench has never run that CLI, it onboards it first. It ends with an HTML run summary open in Chrome and one HANDOFF: line for Prompt 2.

How to use it

  1. Set the CLI up the way you want it measured: the model and effort (/model, or the CLI's config file). The run measures exactly that. The window is pinned for Codex and Copilot (see below), so set the session itself to the same window: Codex model_context_window = 872000 in ~\.codex\config.toml; Copilot /model → long_context.
  2. Open a new session of that CLI in C:\Projects\bench-launch, with full permissions so it runs unattended. Create that folder once, empty: no git repo, no AGENTS.md, CLAUDE.md or .github instructions, so the session is pack-off and every repo command in the prompt uses an absolute path. Do not start the CLI in C:\Projects\x-harness-x-model-bench (the prompt stops if you did). Click Copy prompt below and paste it in.
  3. Its first line names the run and says whether it onboards first: RUN: <RUN_ID> | harness … (known | new: onboarding first) | model … | effort … | context … | session i of n. Its last two lines are SESSION: … (session index and transcript path) and HANDOFF: <RUN_ID>@<worktree>. Paste the HANDOFF line into Prompt 2.
  4. Run 2 sessions per CLI (SESSIONS_PER_CLI): paste the same prompt into a second new session of the same CLI once the first has finished. Each paste is its own run (own name, branch, worktree, 60 cells); the session index counts the runs of that combo since SESSIONS_SINCE, so the second session says session 2 of 2. handoff.json carries session_index and transcript for each, so Prompt 2 can pair the sessions.

You can run several CLIs at once. Each run gets its own name, branch, worktree and cell folder.

A CLI the bench has never run

The first paste into a new CLI (Muse, say) onboards it before the run. The CLI follows docs/runbooks/add-a-harness.md:

  1. Spike. It runs itself headless and finds where it records each session, its token usage, how a second turn continues a session, and its model, effort and context settings.
  2. Write. It adds its own files: a profile, a build entry and pin, a reader that turns its session record into token counts, and, if it does not speak ACP, a small adapter. Tests come first.
  3. Qualify. A one-task probe run in both arms, where every cell must be valid. Then the reader's token counts must equal the CLI's own usage report for the same session, exactly.
  4. Run, then keep it. The full run follows. At the end, the onboarding commit is merged into your local main, so the next paste into that CLI skips onboarding. Nothing is pushed.
The CLI being measured writes the code that measures it. The guards: tests first, a probe where every cell must be valid, and an exact token cross-check against the CLI's own usage report. A CLI with no independent usage report gets its token numbers labelled Inferred. Any gate it cannot pass stops it with no HANDOFF line. Expect the first paste to take noticeably longer than a known CLI's run.

How a run is named

RUN_ID = lean-<UTC yyyymmddThhmmss>-<4 random hex>-<COMBO_ID>, where COMBO_ID = <harness>-<model>-<effort>-<context>. Example: lean-20261013T214502-7c1e-claude-code-claude-opus-5-5-high-1m.

The time and the random part come first because the worktree folder keeps only the first 48 characters of the branch name. Two CLIs started in the same second still get different names.
