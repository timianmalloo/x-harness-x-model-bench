Benchmark: state and target

Proposal, 2026-10-03 · author: the Leader (Claude Opus 5.5, session coord-opus-cq) · evidence: runs/grid-1 to runs/grid-4, their report.html closing sections, and pack-onoff-analysis.html · graph record: benchmark-state-and-target.md

The tool works. It cannot yet answer the question it was built for. harness-bench now runs 276-cell grids across three harnesses with clean integrity checks, and its pack-improvement loop has found and verified real pack fixes. But whether the AI-Forward pack adds rigor, security, compliance and resilience is unmeasured: the task set gives those properties nothing to win on. This page states what works, what does not, and the approach to a benchmark that measures Enterprise/Production value per dollar, per harness.

What does not work

1. The benchmark cannot see what the pack is for the main gap

Most tasks are saturated: both arms pass, so rigor has nothing to improve (grid-4's closing section lists A1–A3, C1, D1–D3, E4–E7, F1, F2 as saturated). The judge metrics that would show quality — spec quality, ADR quality, error handling, assumption disclosure — are not recorded in every grid. No task tests security, compliance, privacy, resilience, rework cost, or the Spike Protocol. The "inconclusive" list dominates every report.

2. No statistical power

Two repetitions over 23 tasks leave every leaderboard row tied (1=) and almost every pack effect "no detectable effect". Run-to-run variance is large: with the same pack-off arm, the leaderboard's tokens per valid cell moved between grid-3 and grid-4 by −14% (Codex) to +24% (Claude Code). Over all cells, not only valid ones, the figures differ (Codex +9%) — the population matters, so the power analysis must name its own. Only large effects can show.

3. Every grid until grid-4 lost data to infrastructure defects

  • grid-1: 24 Claude Code cells skipped (OAuth refresh-token rotation).
  • grid-2: 127 cells skipped (a DNS error and an OAuth expiry both misclassified as "model unavailable"); E2–E5 unscored (the grading copy lived inside the repo, so uv found the wrong project).
  • grid-3: G2 unscored (a hand-derived statement hash and an artifact scan that flagged the build output the prompt requires); 5 cells lost to a 1 MiB line bound.
  • grid-4: G2 scores clean on every formal check but cannot rank — scenario 7 has no pass@1 definition.

Each fix was right. Finding one per grid, at about 10 hours per grid, is why this has taken weeks.

4. The cycle is slow

A grid takes about 5 h to run and 5 h to grade (measured, grid-3 and grid-4). A gate ring takes about 85 min. Many fixes needed a gate ring and a re-grade before the next grid.

5. The process mirrored the pack's own problem

Rulings, sweeps, gate rings and re-reviews made the tool trustworthy, and they consumed most of the time — the same ceremony-versus-outcome trade-off the analysis found in the pack. The Leader added defects too: two watchers that silently stopped working, a mutation committed to main, a re-grade trusted to recover G2 that could not, and misquoted figures almost pushed upstream.

6. Prose rules do not hold

"Never set a git identity" was written down; 4 cells per grid still did it (PK-07). Fix 3's opt-in rule was defeated by the pack's own start marker creating docs/audit/ (51 grid-4 cells). Rules held only when a mechanism enforced them.

This verdict is about these tasks, not the pack's thesis. A task set where both arms pass cannot reward rigor; one with no security or resilience requirement cannot reward secure-by-default work. The data says the pack is expensive; it does not yet say whether it is worth it.

The target

A benchmark that answers, with a stated confidence: "Does pack version X deliver better Enterprise/Production outcomes per dollar than pack-off and than pack version Y, on each harness?" — where "outcome" includes correctness and security, resilience, rework avoided and simplicity, each checked mechanically, and the answer arrives in hours, not days.

Proposed approach

A. Tasks that can show value largest gap

Build an Enterprise/Production task family (sketched in enterprise-production-portfolio.html; none of it is built). Each task is unsaturated, multi-step, on an existing codebase, and carries a hidden mechanical check for the property the pack claims to improve:

  • Security by default — a feature request whose naive implementation is exploitable; hidden tests attack it (injection, authorization bypass, secret leakage).
  • Resilience — a change to code that calls an unreliable dependency; a fault-injection harness checks timeouts, retries, idempotency.
  • Rework cost — a two-turn task: the second turn's requirement punishes a short-sighted first design; measure the second turn's diff size and failures.
  • Spike Protocol / no guessing — an unfamiliar or deliberately unusual API whose plausible guess is wrong; hidden tests fail on the guessed contract.
  • Simplicity — a task with an obvious over-engineered path; measure added abstractions and lines against a reference, with correctness held fixed.

Keep a few saturated calibration tasks; stop spending most of the budget on them.

B. Quality metrics that record

Prefer mechanical proxies (hidden attack tests, fault injection, diff-size and abstraction counts, assumption-marker detection). Where only judgment works, enable the judge rubric with a calibrated jury and report agreement; never leave a metric that the report shows but no pass records.

C. Enough power

Run a power analysis from grid-3/grid-4 variance before the next full grid. Expect fewer tasks with more repetitions, paired by task, and a pre-registered primary metric per question, so an effect has a stated minimum detectable size.

D. A faster, more stable loop

  • Pilot ring: one repetition of every task before a full grid, graded immediately, so a grader defect costs an hour, not a grid.
  • Pack-regression ring: a small fixed subset (a few hours) for each pack change; the full grid runs only to answer a pre-registered question.
  • Parallel grading: grading is half of every grid's wall clock.
  • Engine freeze: no grader or engine change during a measurement campaign except a recorded defect fix.

E. Pack direction the data already supports

  • Simplify aggressively: fixes 4–6 — shrink the always-loaded context (AGENTS.md block 26.5 KB; Copilot's always-applied set 241 KB) and make T0 mechanical. This is the largest measured cost lever left.
  • Mechanism over prose: every rule the data shows matters gets a hook or a test (fix 3b is the first: the start marker and git identity).

Sequence

  1. Freeze the engine at the current main, except recorded defect fixes (scenario-7 pass@1; the pack section counting a missing pass@1 as a fail).
  2. Specify the Enterprise/Production task family and its metrics (this proposal's next step: /specify).
  3. Power analysis from grid-3/grid-4 → repetitions and task count for the target effect sizes.
  4. Build 4–6 tasks (one per property above) and the pilot ring; prove each task's oracle through the engine (reference solution passes, a seeded naive solution fails).
  5. Build a slimmed pack (fixes 4–6 and 3b) as pack version Y.
  6. One well-powered grid: pack-off vs current pack vs slimmed pack, three harnesses, the new tasks plus a small calibration set.

How we know it worked

  • The next grid's report gives each pack property a verdict (hit / miss) with an interval, not "inconclusive" — for at least security, resilience and rework.
  • No full grid loses data to a grader or engine defect (the pilot ring caught it first).
  • A pack change can be evaluated in under a working day on the regression ring.
  • The pack-on cost ratio is reported next to the value it bought, per harness, and the slimmed pack is no worse on value at materially lower cost — or the data says plainly that it is.

What we stop doing

  • Running full grids on the current task set to measure pack changes: it will keep showing "the pack costs more and gains nothing measurable" until the tasks can reward rigor.
  • Discovering grader defects in full grids.
  • Writing rules as prose where the data shows they matter.
