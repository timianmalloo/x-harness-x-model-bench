Interactive run: one CLI session per arm, the way a developer works

Two windows per CLI: one in a pack-on folder, one in a pack-off folder. Every window gets the same single paste and works through all 11 lean tasks one at a time, as one long developer session. Nothing is launched headless. When a session finishes its last task, it grades itself with the bench's own graders and opens its report in Chrome. Afterwards one prompt gathers the graded runs and compares them. The headless run (lean-benchmark-run-prompt.html) stays as the automated alternative.

1. Prepare the folders (one command for every CLI)

In any PowerShell window:

cd C:\Projects\x-harness-x-model-bench
uv run bench interactive prepare --harness claude, codex, copilot

List the CLIs you want: claude (or claude-code), codex, copilot, agy. Commas, spaces or both are fine. You do not name the tasks or the pack:

  • Tasks: every lean task (S1, S2, RS1, RS2, RW1, RW2, NG1, NG2, SM1, SM2, SV1), read from the lean ring bench\rings\lean.yaml.
  • Pack: the latest AI-Forward pack, the HEAD of C:\Projects\ai-forward. Prepare prints the commit and revision it used. Pull that clone first if you want what is on its remote.

For each CLI it prints two folders, C:\Projects\bench-interactive\int-CLI-<UTC time>\off and …\on. Each holds the 11 task folders (base trees only; the hidden tests stay in the bench) and .bench\next.py, which hands out one task at a time. on also has the pack installed at its root; off holds no instruction file (prepare checks). Each arm also gets its own Python environment, .venv, made from your default python, so a session's pip install never reaches the other arm or your global Python. Both arms get one git line-ending rule, and prepare checks that their task files match byte for byte. Prepare takes about a minute per CLI. For a second model of the same CLI (Copilot with gpt-5.5, say), run prepare again for that CLI. --tasks and --pack SOURCE@COMMIT still override the defaults.

2. Launch the CLI in each folder (two windows per CLI)

In each window, cd into the folder, activate its environment, then start the CLI with the line for it below. Both windows of one CLI use the same line. When the CLI asks whether to trust the folder, say yes in both.

.\.venv\Scripts\Activate.ps1
$env:PIP_REQUIRE_VIRTUALENV = "1"

The first line makes the session's python and pip the arm's own. The second refuses any pip install that would land outside an environment. If you skip them, the report says the session shared an interpreter.

3. While it runs, and how each run ends

  • Leave the windows alone. Expect 1 to 4 hours: 11 tasks, two of them in two turns (13 hand-outs).
  • If a session stops early and asks you something, answer continue. An unfinished task is graded on what is in its folder.
  • Each run grades itself. The next.py call that prints ALL DONE also starts that arm's grading in the background: bench interactive collect RUN --arm ARM --open, the bench's own graders on a replay of each task folder. The session is not told. When it finishes, the arm's report opens in Chrome (RUN\collect\ARM\report.html): hidden tests, property check, drift per task, minutes, tokens and tool calls so far, and warnings.
  • Exit the CLI only after its report has opened (/exit, or Ctrl+C twice). The CLI then writes the end of its record; Copilot writes its token totals only at this point.
  • If no report opens within about 10 minutes, read RUN\grade-ARM.log. A failed grading opens RUN\grade-ARM-failed.html instead. To grade by hand, from the bench repo: uv run bench interactive collect RUN --arm ARM --open.

What the report can and cannot say

  • Graded the same way as a headless cell. Pass/fail and each property check come from the bench's own graders. Each task folder is replayed onto a fresh copy of its base tree, the path bench discriminate uses. Each task is graded as next.py copied it at its hand-off, so a later task's edit to its folder is not graded and is reported as a warning. The two-turn tasks are graded on both turns' copies. Drift is the bench's change-set drift (changed lines outside each task's blast radius). The catalog's process metrics and attention drift need a record per task and are not graded here.
  • Tokens and tool calls per task come from each session's record, split at the next.py calls. The report that opens at the end of a session read the record while the session was still open; gather reads it again after you exit, and the comparison uses those numbers. A session's record is the one launched in that arm's folder, never one that merely mentions it. A next.py call that handed nothing out, because it was blocked or a command before it failed, is not a task boundary. Copilot's per-call usage rows give per-task tokens; after exit they are used only when they add up to its session total. agy is read from its conversation database (field map checked against 1,542 requests).
  • Finished work is committed. When next.py closes a task, it commits that task's folder, and only that folder, so a later task's git stash or reset cannot take it.
  • One session per arm, with the tasks in the same fixed order in both arms. Context carries from task to task, as in real use. That is why this mode is not comparable with the headless runs.
  • A deleted file cannot be replayed, and the report lists any. So does a session that read the queue file directly or never reached a task.
